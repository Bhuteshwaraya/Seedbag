# Seedbag 0.3.5 validation

The release program passed **113 tests**, with zero failures, errors, or skips, on Windows 11 using Python 3.12.14 and Git 2.53.0.windows.3. The run took 109.582 seconds. The included `validation/tests.json` identifies the exact tested Python files by SHA-256; `validation/tests.txt` contains the complete named results. The public repository also runs the suite through GitHub Actions on Windows and Ubuntu with Python 3.11 and 3.12; consult the run for its result rather than treating configuration as a passing check.

The assistant or maintainer runs the included suite from this package. This is not a project-creation step for the user:

```sh
python -B -m unittest discover -s tests -v
```

Use an available Python 3.11+ executable. Git tests use disposable local repositories and local bare remotes. They do not require GitHub access, change a live project, or execute effects against an external service. Some fixtures remain under the command's `work/` directory for inspection.

Coverage: 23 continuity and adversarial scenarios, 14 context/view scenarios, 26 Git scenarios, 12 installed-CLI/reporting scenarios, 29 setup-probe scenarios, and 9 initial connector-export scenarios. The checks cover source/disposition rules, pending input, stale transactions, history preservation, changed files and requirements, check provenance, interrupted actions and rendering, exact context budgets, generated-view edits, portable interpreter resolution, explicit incomplete savepoints, staged-file correctness, merge parents, shallow history, committed rollback, fresh-clone recovery, license-notice propagation, and a real local commit hook. The installed lifecycle checks that the permanent continuation prompt contains the project locator, contains no executable setup command, and remains byte-identical through project updates and a fresh clone. It verifies that the first-time guide and helper travel with the project and that the cloned helper runs offline.

The recovery checks reject missing required files in the snapshot even when they still exist in the working folder, mismatched README/continuation blocks, a wrong repository locator, malformed prompt blocks, and rewritten continuation files compared with parent commits. A committed audit detects a rewrite even after the local hook was bypassed. The CLI verifies the README and identical saved prompt survive publication and cloning. A separate synthetic lifecycle prepares an unpublished temporary workspace, publishes its complete files to a local bare remote, and restores them in a later local directory. This exercises the file and Git mechanics; it is not a launched Work cloud conversation.

Setup probes use deterministic subprocess fixtures for missing Git/CLI, absent or unreadable credentials, actual rejected credentials, network/TLS errors, access denial/rate limits, a valid account with an unreadable existing Git key, and successful read probes. They check secret-output suppression, preserved transport configuration, optional CLI behavior, offline execution without auth/network calls, and explicit validated network targets. These fixtures do not create an account, install missing software on a clean OS, or prove private repository push permission.

Additional setup cases distinguish helper launch/crash diagnostics, repository ownership, SSH host verification, malformed key data, and inaccessible keys. They verify that recommended actions use fixed text, recommend reuse after successful probes, remain local-only offline, and do not add probes or automatic login, repairs, or protocol changes. The new device-persistence guide was reviewed against current primary documentation; the package does not itself write host-wide configuration or prove future account access.

The earlier live project-creation test stopped at an unreadable configured Git key, correctly distinguished from authenticated API access. A later independent read-only test, after access was restored outside the package, successfully retrieved an existing private project made with Seedbag 0.3.1. Both a normal Git clone and a connector snapshot matched all 16 files at the selected GitHub commit. The four executable Python files matched the verified published package; the project's own context and doctor commands restored the same records with no readiness problems. Both copies remained byte-for-byte unchanged and the clone stayed clean. This demonstrates real private GitHub retrieval into local files and runtime recovery, not new-repository creation, push permission, or automatic cloud-to-local routing by a fresh conversation. Private project names, content, and identifiers are excluded from this public package.

An earlier Work cloud attempt using the 0.3.3 creation prompt failed before planting or publishing: its connector lacked repository creation, and its shell Git had no authenticated route. An incomplete-setup handoff was correctly distinguished from a saved project.

A later controlled experiment used the unchanged 0.3.4 runtime in an actual Work cloud conversation. Codex first provisioned a private README-only repository. Work planted the project, recorded the test input and fixture, ran its runtime and snapshot checks, and used connected GitHub tools to publish the exact audited 17-file tree. The offline preparation commit and remote commit had different parents and IDs; their trees matched. This was an assisted test procedure, not the existing ordinary `publish` command or an unassisted creation prompt.

A fresh local Codex subagent received only a short natural project request and repository link as project context. Its test harness specified the destination and a stop before changes, but supplied no expected marker or prior project conversation. It created a real local Git checkout and recovered the exact marker, purpose, unresolved question, and next work from the repository. After the writer handoff, it used the installed runtime to record local resumption, run a declared continuity check, and publish a new private checkpoint through ordinary Git. Independent committed-object and remote-ref checks confirmed a direct descendant, the original five ledger events preserved as a prefix, unchanged installed files and permanent continuation file, and a clean local checkout. This was an isolated agent in the current task, not a separately created user-facing Codex task. Private project identifiers and content are excluded from this package.

Work also reported an intermediate revision-4 command result followed by a readable revision-2 ledger. It preserved the observed earlier prefix and reconstructed the absent assistant captures through the runtime; the final capture texts and committed snapshot were verified. No copy of the initially reported revision-4 ledger was retained, so the cause remains unknown. One later command did demonstrably save a capture before failing to render a generated view. Version 0.3.5 adds explicit partial-save/readback reporting for that case, including unverified state when returned and observed identities differ. It does not claim to fix the unexplained apparent rollback or prove uninterrupted cloud persistence.

The new initial exporter is tested separately: exact binary bytes and modes, selected committed data despite working/index changes, valid snapshot requirements, parentless-only history, repository locator, safe output, overwrite refusal, and explicit prepared-not-shared status. It does not call GitHub or attest the assistant's remote observations. The full 0.3.5 creation prompt and exporter were not rerun live in the Work conversation; the live test used the documented procedure manually with 0.3.4. Initial repository provisioning still required assistance. Short saved-request generation and the README-to-AGENTS route have automated coverage; the live reader used a short request to recover the existing 0.3.4 project.

Controlled document reviews also cover newcomer setup, existing working connections, broken transport, and unavailable computer-local files. These do not prove universal assistant compliance. Clean-OS dependency installation, new-account sign-in, and unassisted current-release creation remain unverified.

The creation prompt and assistant bootstrap protocol are also reviewed as an interface: the person supplies a name and project goals, while the assistant handles technical setup and capability routing. This review does not prove that every AI application will follow the prompt or possess the required tools. An unavailable capability requires a complete handoff and an honest saved/shared status, not a fabricated installation.

The guarantees apply to cooperating use of this program. Tests do not establish universal semantic completeness, automatic chat capture, authentication of recorded source labels, every-platform compatibility, distributed exactly-once execution, or long-term performance. A declared test is only as good as its assertions and input coverage. Git hooks can be bypassed; the committed-snapshot audit is available for a reviewer or CI, but no remote branch protection is installed by this package.

`MANIFEST.json` inventories the package bytes, excluding the manifest itself. Planted projects receive their own program copy and never auto-update from this seed. The version number alone does not replace exact source identity when comparing development fixtures or releases.
